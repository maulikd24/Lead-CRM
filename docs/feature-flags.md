# Feature flags and environment variables

The **Default** column is the value the registry declares (`src/lib/flags/registry.ts`, see `defaultFor`): feature, outbound and outbound-ai switches declare **on** (`1`), except a switch with an approval note (live messaging, closed-loop conversions, Google Chat lead alerts), which declares nothing; WA_META_WINDOW and CONSENT_ENFORCEMENT declare nothing either, because their runtime readers act only on the exact value `1`. Blocked, test and in-flight names, and the other safety switches (demo, sample data, SSO-only, kill switches), declare off. The tables are generated; run `npm run flags:docs` after changing the registry. **Caveat:** the runtime readers in the code still treat an unset flag as off (a flag is on only for the exact value `1`), and the Admin Flags panel shows the runtime state. A declared default of on is therefore not yet applied at run time until the readers use it; see the notes on the all-on profile in `src/lib/flags/profiles.ts`. Variables named `NEXT_PUBLIC_*` are inlined at **build** time (changing one needs a rebuild); all others are read at run time.

### Validation rules

`validateFlags(env)` checks these. In a production start the safety rules (FR-05, FR-10, FR-11, FR-13, FR-14) stop the boot; every other finding is logged once and shown on the Flags tab. Set `FLAG_CHECK=warn` to downgrade a failed check (break-glass, logged loudly). In development and CI everything is reported.

| Rule | Severity | Checks |
| --- | --- | --- |
| FR-01 | error | Unknown name: a NEXT_PUBLIC_* name, or a name read in the source, that is not in the registry |
| FR-02 | error | Bad value: a bool that is not 1 (true, yes and on are silently off), or an enum, int or url that does not parse |
| FR-03 | error | A requirement of the flag is not satisfied |
| FR-04 | error | A conflict of the flag is present |
| FR-05 | error | A blocked flag is on (autonomous ad-spend changes) |
| FR-10 | error | Outbound or vendor-sharing needs consent enforcement and the consent screens |
| FR-11 | error | Closed-loop conversions need the full consent chain and may not be record-only for ads measurement |
| FR-12 | error | AI features need a provider key (error) and a recorded sign-off (warning: not readable from env) |
| FR-13 | error | No live outbound, production or hosted database under demo; the build-time twin must match |
| FR-14 | error | Sample partner data conflicts with a production environment |
| FR-15 | error | Single sign-on pairing: SSO_ONLY needs SSO and a break-glass list; SSO needs its three settings |
| FR-16 | error | Secret and setting pairing, and the always-required secrets |
| FR-20 | warn | Soft prerequisite: a screen that renders empty or unreachable without another flag (an error in profiles for the marketing-gated four) |
| FR-30 | warn | Build-time mismatch: a NEXT_PUBLIC_* value differs from what the running bundle was built with (a rebuild is pending) |
| FR-31 | warn | Deprecated or unreferenced registered flag: registered, but nothing in the source reads it |

## Daily brief: SendGrid sender authentication (owner steps)

The brief is sent through SendGrid, so mail from `BRIEF_FROM` must be authenticated for the domain it uses. Do these once, before turning `DAILY_BRIEF_ENABLED` on. The DNS values are not written here: SendGrid generates them for the account, so copy them from its screens.

1. In SendGrid, open **Settings, Sender Authentication**, then choose **Authenticate Your Domain**. Enter `allvest.co` and pick the DNS host that manages `allvest.co`.
2. SendGrid shows the DNS records to add. Add **every** record it lists for the domain. This includes the **DKIM** CNAME records (usually two, each with a name ending in `_domainkey`) and the **SPF** TXT record. Copy names and values exactly as displayed. Do not retype them from memory or from this file.
3. SPF: a domain may have only one SPF TXT record. If `allvest.co` already has one (for example for Google Workspace), merge SendGrid's entry into that record instead of adding a second one. Two SPF records fail authentication.
4. If SendGrid also lists a link-branding or return-path CNAME for the domain, add it as shown.
5. Back in SendGrid, click **Verify** and wait for DNS to propagate. Retry until the domain shows as verified. DNS can take a while; there is nothing to fix on the app side while it waits.
6. Create a SendGrid API key with **Restricted Access** and only the **Mail Send** permission. Put it in `SENDGRID_API_KEY`.
7. Set `BRIEF_FROM` to an address on `allvest.co`, for example `Allvest CRM <crm@allvest.co>`. The app reads it from the environment at run time (no code change).
8. Run a dry run first: `POST /api/internal/cron/daily-brief?dry=1` with the `x-cron-secret` header. It sends nothing. Then set `DAILY_BRIEF_ENABLED=1`. The brief goes out only from the 09:00 IST tick.
9. After the first send, check **Activity** in SendGrid. A message with status "delivered" confirms the setup.

If a run lists RMs under `pending` in its result, do not expect a retry. A pending row means a send may have gone out before a crash. Check those RMs' inboxes and SendGrid Activity before deciding anything.

## How the partner and referral flags combine

The partner first touch is written by the lead intake only when `PARTNER_WORKSPACE_ENABLED=1`; the referral hook runs only when `REFERRAL_PROGRAM_ENABLED=1`. A partner code is always the partner's; a customer referral that also matches is recorded and flagged for review only when the partner credit was written. See `docs/referrals.md`.
