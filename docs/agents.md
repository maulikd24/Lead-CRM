# AI agents (WhatsApp drafts)

Agents prepare drafts. They never send anything on their own.

- Draft-only: an agent reads a conversation and proposes a message. The proposal waits in "Agent drafts".
- Per-message approval: nothing is sent until the assigned RM or an Admin approves that specific message.
- Kill switch: an agent runs only when BOTH the `AGENT_NUDGER_ENABLED=1` environment flag (only the exact value `1`) and its enabled row in `AgentSetting` are on. Turning either off stops new drafts.
- Guardrails: every draft passes a regex check and an LLM judge before it is shown. A draft that fails is not offered.
- Production enablement requires a recorded compliance sign-off (including the data-protection notice and lawful basis for processing chat content). That record is kept outside this repository.
- Consent: with `CONSENT_ENFORCEMENT=1` the nudger skips customers without marketing consent ('no consent'), and reply assist should call `assertConsent`. See docs/consent.md.
- Insights: with `NEXT_PUBLIC_INSIGHTS=1`, Admins and Managers get `/agents/insights` (link on the Agent drafts page and in Cmd+K). It shows aggregate response analytics, agent quality and an ESTIMATED cost per approved message from the price table in `src/lib/insights/pricing.ts` (assumed list prices, not billing data; unknown models show n/a). Suggestions are rule-based. `assignVariant` in `src/lib/insights/variant.ts` is ready for future experiments and is not used by the nudger.
  The cost estimate covers the drafting calls only: token usage of the guardrail judge call is not stored, so real spend is higher. Follow-up (needs a reserved migration prefix, not done yet): add indexes `Message(direction, channel, createdAt)`, `InteractionOutcome(createdAt)` and `AgentProposal(decidedAt)` because the insights queries scan without them, and optionally store judge token usage.

## Suggested replies in the inbox (`wa_reply`)

A two-way assistant that drafts a reply to a customer's WhatsApp message. The RM reads, edits and presses Send; the assistant never sends.

- Flags (all off by default): `WA_ASSIST_ENABLED=1` (exact value `1`) AND an enabled `AgentSetting` row for `wa_reply` (same kill switch as the nudger). `WA_ASSIST_AUTO=1` additionally drafts once when an RM opens a conversation whose last message is an unanswered customer message. With the flags off the panel is not rendered at all.
- No model call in the ingest path: the model is called only from inbox server actions ("Suggest a reply", or auto on open). There is no cron batch. The one ingest addition is a model-free regex check (`needsHandover`), run only when `WA_ASSIST_ENABLED=1` and the agent row is enabled, wrapped so it can never fail or slow ingest; with the flags off ingest does nothing extra.
- Data protection: chat content is sent to the AI vendor in the minimised form described below. Recorded data-protection sign-off (notice and lawful basis) is required before enabling this in production; that record is kept outside this repository.
- What the vendor sees: first name, language (English, Hindi or Hinglish, mirrored from the customer's latest message), a fixed reason category, and the last up to 6 messages labelled Customer/RM. The excerpt maps Devanagari digits to ASCII, cuts every link to its bare host, and strips phone numbers (any separators), dates of birth, emails, PAN (spaces allowed) and any 6+ digit run; it drops the customer's surname (with ji/sahab/bhai suffixes), caps each message at 300 characters and the total at 1200. Briefing free text and history never leave. The briefing is the side-effect-free `buildAgentBriefing(clientId, { persist: false })`.
- Behaviour rules in the prompt: answer only the question, briefly; no advice, returns or recommendations; never invent account facts; ask a clarifying question or offer a call when unsure; conversation text is treated as untrusted.
- Safety: every draft passes the regex guardrail and the LLM judge. A failure is stored as `BLOCKED`, shown as "Could not draft safely" (the text is never shown), and never sent.
- Handover: if any unanswered customer message trips `needsHandover` (also at ingest when flagged on), or the briefing has an open issue or do-not-discuss topic, no model call is made. A `BLOCKED` marker `HANDOVER: ...` is stored and the banner stays until the RM replies, however many follow-ups arrive. Recording is idempotent and leaves a trace the nudger respects: an OPEN COMPLAINT insight, a task (`wa_handover:<clientId>`), an activity entry, and notifications to the assigned RM and their manager (managers/admins if unassigned). It deliberately does not call `recordInteractionOutcome(RM_HANDOVER)`: that refreshes intelligence and can enrol journeys that send without approval.
- One open suggestion per conversation (a conversation is one client). A newer customer message, or Regenerate, expires the previous open draft with the compare-and-set transition `DRAFT -> EXPIRED`. Drafts expire after 24 hours. At least 10 seconds must pass between two generations for one conversation. Model refusals produce no draft. The "Agent drafts" page hides `wa_reply` rows and refuses to approve or reject them (only `wa_nudger` drafts go through it); inbox suggestions are dismissed with their own compare-and-set.
- Outcome metrics use existing columns, no new enum: `SENT` with `body = originalBody` is used as is, `SENT` with a different `body` was edited, `REJECTED` is dismissed, `EXPIRED` is superseded or regenerated, `BLOCKED` is blocked or a handover (`usageOf` in `reply-assist-lifecycle.ts`). `decidedById`/`decidedAt` record who and when; `inputTokens`/`outputTokens` hold the draft call's token counts (the judge call is not counted).
- 24-hour service window (`src/lib/whatsapp/service-window.ts`): helpers are pure and tested. Enforcement (composer warning and send refusal) is behind `WA_META_WINDOW=1`, default off, and applies only to a Meta Cloud API account. `WhatsAppAccount` carries no provider field today, so the provider of the reply account cannot be determined and enforcement stays off; once accounts carry a provider, `accountProvider()` reads it and the flag can be switched on. Linked-device accounts are never subject to the rule.
- Production enablement requires a recorded compliance sign-off (including the data-protection notice and lawful basis for processing chat content). That record is kept outside this repository.
